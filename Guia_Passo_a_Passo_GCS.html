2. Passo a Passo: O que fazer em cada etapa

Passo 1: Enviar o Commit Local para o GitHub

O repositório local já está com o commit pronto (1 commit à frente de origin/main). No PowerShell, execute:

cd c:\Users\Cliente\Downloads\atividade\openfoodfacts-main
git push origin main
Dica de Autenticação: Como o GitHub descontinuou o uso de senhas simples para operações Git, se for solicitado login, use a opção Sign in with your browser ou insira o seu Personal Access Token (PAT) gerado em GitHub > Settings > Developer Settings > Personal access tokens.

Passo 2: Configurar o Par de Revisão com Acesso de Escrita

  1. Abra o repositório no navegador: https://github.com/MateusIsidoro/openfoodfacts
  2. Clique na aba superior Settings.
  3. No menu lateral esquerdo, na seção Access, clique em Collaborators.
  4. Clique no botão verde Add people.
  5. Pesquise pelo nome de usuário ou e-mail do seu colega/dupla de trabalho.
  6. Defina a função/permissão como Write (Escrita).
  7. Clique em Add to this repository. O colega receberá o convite para aceitar.

Passo 3: Configurar a Proteção da Branch main

  1. Ainda em Settings, no menu lateral esquerdo, clique em Branches.
  2. Clique em Add branch protection rule (ou Add rule).
  3. No campo Branch name pattern, digite: main
  4. Marque as seguintes opções essenciais:
    • ☑️ Require a pull request before merging
    • ☑️ Require approvals e deixe o valor em 1 (exige a revisão do par de escrita).
    • ☑️ Dismiss stale pull request approvals when new commits are pushed.
    • ☑️ Require status checks to pass before merging (marque o check ci do pipeline).
    • ☑️ Do not allow bypassing the above settings (impede que qualquer usuário, inclusive o administrador, faça push direto).
  5. Role até o final da página e clique em Save changes.

Passo 4: Gerar e Capturar a Evidência de Recusa do Push Direto

Com a regra de proteção salva, comprove no terminal que o push direto é recusado:

  1. No terminal do projeto, crie uma alteração de teste simples: 
    "teste de bloqueio" >> test_recusa.txt
git add test_recusa.txt
git commit -m "teste: tentativa de push direto sem PR"
  2. Tente enviar o commit diretamente para a branch principal: 
    git push origin main
  3. O GitHub recusará a operação e exibirá no terminal a evidência formal: 
    To https://github.com/MateusIsidoro/openfoodfacts.git
 ! [remote rejected] main -> main (protected branch hook declined)
remote: error: GH006: Protected branch update failed for refs/heads/main.
remote: error: Changes must be made through a pull request.
remote: error: 1 review approving this pull request is required before merging.
error: failed to push some refs to 'https://github.com/MateusIsidoro/openfoodfacts.git'
  4. 📸 Registro de Evidência: Tire um print desta tela do terminal com a mensagem de erro acima. Ela é a prova obrigatória de que a política de GCS está ativa e funcional.
  5. Desfaça o commit de teste para limpar o histórico local: 
    git reset --hard HEAD~1

Passo 5: Configurar os Environments staging e production

  1. No GitHub, acesse a aba Settings do repositório.
  2. No menu lateral esquerdo (sob Code and automation), clique em Environments.
  3. Clique no botão New environment.

5.1 Criando o ambiente staging:

  1. Digite o nome: staging e clique em Configure environment.
  2. O ambiente de homologação não exige revisores prévios, permitindo deploy automatizado pós-merge.
  3. Clique em Save environment.

5.2 Criando o ambiente production com Revisor Obrigatório:

  1. Volte em Environments e clique em New environment.
  2. Digite o nome: production e clique em Configure environment.
  3. Na seção Deployment protection rules, marque:
    • ☑️ Required reviewers
  4. No campo de busca de revisores que surgir, pesquise e selecione o seu usuário: MateusIsidoro.
  5. Certifique-se de que a opção Prevent self-review esteja desmarcada para que você possa aprovar as suas próprias promoções de versão.
  6. Clique em Save protection rules.

3. Fluxo de Trabalho Integrado (Como apresentar e testar)

Após as configurações acima, o fluxo contínuo de trabalho e auditoria funciona da seguinte forma:

  1. Criação da Branch de Mudança:
    git checkout -b feature/melhoria-nutricional
  2. Envio e Abertura de PR:
    git push -u origin feature/melhoria-nutricional
    Abra o Pull Request no GitHub apontando para a main.
  3. Execução da CI:
    O GitHub Actions executa o job ci (verificando formatação, flutter analyze e flutter test).
  4. Revisão por Par com Acesso de Escrita:
    Seu colega convidado acessa o PR, revisa as alterações no código e clica em Review changes > Approve.
  5. Merge na Main:
    Com o CI verde e a aprovação do par, o botão de merge é liberado.
  6. Deploy em Staging e Gate de Produção:
    O pipeline inicia automaticamente o deploy no ambiente staging.
    Ao concluir Staging, o pipeline fica em espera no ambiente production com a indicação Waiting for review.
    Você (Mateus Isidoro) clica no botão Review deployments, marca production e clica em Approve and deploy para concluir a entrega final.
